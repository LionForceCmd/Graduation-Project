# Отчёт по выпускному проекту

**Название выбранного проекта:** Система знаний команды (вариант E): поиск по своим документам и ответы с источниками.

## Ценность (для кого и зачем)
Для новичков, менеджеров и тимлидов небольшой команды. Знания о правилах, процессах и шаблонах ответов лежат в разных документах, поиск занимает время, а если искать некогда, ответ начинают додумывать. Система хранит документы, отвечает на вопросы только по найденным фрагментам, прикладывает цитаты и честно говорит «данных недостаточно», если подтверждения нет.

## 3 сценария пользователя
1. **Загрузка документов.** Пользователь вставляет текст или загружает файл `.txt/.md` на вкладке «Документы» и видит документ в списке.
2. **Вопрос и ответ.** Пользователь задаёт вопрос на вкладке «Вопросы» и получает ответ с цитатами-источниками, по клику документ открывается с подсвеченной цитатой.
3. **Ручная проверка.** Подходящих фрагментов нет или уверенность низкая: пользователь видит «данных недостаточно», метку «требует проверки», причину (например, `NO_SOURCES`) и подсказку, что сделать. Запись доступна в «Истории» (фильтр) и в «Аудите».

## Точки доступа API
| Метод и путь | Назначение |
|---|---|
| `POST /kb/documents` | добавить документ (`title`, `text`); 422 при пустых или слишком длинных полях |
| `GET /kb/documents` | список документов для витрины (`id`, `title`, `created_at`) |
| `POST /kb/ask` | вопрос → `{answer, sources[{document_id, quote}], needs_review}` (+ `confidence`, `reason`, `run_id`) |
| `POST /ai/answer_with_sources` | ИИ-операция отдельно: `question` + `context` → строгий JSON |
| служебные для панели | `GET /kb/documents/{id}`, `GET /qa`, `GET /qa/{id}`, `GET /audit`, `GET /export/qa`, `GET /export/audit`, `GET /health` |

## Схема данных (SQLite)
- `documents(id, created_at, title, text)`
- `snippets(id, created_at, document_id, snippet_text)`: абзацы документов, по ним идёт поиск
- `qa_runs(id, created_at, question, answer, sources_json, needs_review, error, confidence, provider, raw_output, duration_ms)`
- `audit_runs(id, created_at, action, input, output, status, error, duration_ms)`: запись для каждой команды сервиса, в том числе неудачной

## ИИ-операция
**Схема JSON (строгая, 4 поля):**
```json
{"answer": "string",
 "sources": [{"quote": "string"}],
 "confidence": "high|medium|low",
 "needs_review": true}
```
**Температура:** 0.1 (меньше «творчества»); ограничение длины ответа 400 токенов, контекст 4096.
**Режимы:** `mock` (без модели, ответ собирается из лучших предложений найденных абзацев) и `ollama` (локальная модель, по умолчанию `qwen3.5`, структурированный вывод по JSON-схеме). Проверки после ответа одинаковы в обоих режимах.
**Когда нужна ручная проверка (`needs_review=true`):**
- поиск не нашёл подходящих абзацев (`NO_SOURCES`; модель в этом случае не вызывается);
- `confidence="low"` (`LOW_CONFIDENCE`);
- у ответа нет ни одной проверенной цитаты (`NO_SOURCES`);
- модель вернула не JSON или JSON не по схеме (`INVALID_JSON`, `SCHEMA_MISMATCH`), показывается резервный ответ из цитат.

Инвариант: `needs_review=false` ⇒ `sources` не пустой; `sources` пустой ⇒ `needs_review=true`.

## Память / контекст
Хранится: документы целиком, их абзацы (`snippets`), история вопросов и ответов (`qa_runs`) с источниками и причиной проверки. Используется так: вопрос → поиск по абзацам (нормализация слов + BM25, порог покрытия слов вопроса 45 %) → до трёх лучших абзацев становятся контекстом для ИИ-операции. Модель видит только их, а не всю базу.

## Контроль качества
**На входе:** пустые `title`/`text`/`question` и превышение лимитов (200 / 50 000 / 500 символов) → 422 и запись в аудит; неизвестный документ → 404.
**На выходе:** JSON проверяется схемой (pydantic); каждая цитата сверяется с найденным текстом (дословно, без учёта регистра и переносов строк) — выдуманные цитаты отбрасываются; нет источников или низкая уверенность → `needs_review`; недоступность Ollama не ломает сервис (резерв — режим mock, причина `LLM_UNAVAILABLE` в аудите).
**Автотесты:** `pytest` (19 проверок) и `scripts/eval.py` (10 вопросов с ожиданиями).

## План внедрения за 1 день
- **Утро (2–3 ч):** развернуть (`docker compose up`), загрузить 10–20 реальных документов команды, прогнать 10 типовых вопросов.
- **День (3 ч):** дать пользоваться трём коллегам; по вкладке «История» с фильтром «требует проверки» собрать вопросы без ответа и дописать недостающие документы.
- **Вечер (1 ч):** настроить порог `MIN_COVERAGE`, запустить на общем компьютере или сервере, разослать ссылку команде.

## Мини-экономика
Допущения «на салфетке» (замените своими цифрами): поиск ответа вручную по документам и чатам занимает в среднем 5 минут, с системой — 30 секунд; стоимость часа сотрудника — 1 000 ₽.

| | До (вручную) | После (система) |
|---|---|---|
| Время на 1 вопрос | 5 мин | 0,5 мин |
| 100 вопросов | 500 мин ≈ 8,3 ч ≈ 8 300 ₽ | 50 мин ≈ 0,8 ч ≈ 830 ₽ |
| Прямые расходы на ИИ | — | 0 ₽ (локальный запуск, без платных API) |

**Вывод:** экономия около 7,5 часов (≈ 7 500 ₽) на каждые 100 вопросов. Кроме времени, система даёт проверяемые ответы (цитата и документ) и показывает, какие знания не записаны (вопросы с меткой проверки).

## Риски и меры снижения
1. **Выдуманный ответ модели** → ответ только по найденным абзацам, температура 0,1, проверка цитат на дословность, нет источников = ручная проверка.
2. **Модель вернула не JSON / не по схеме** → строгая схема, коды `INVALID_JSON` и `SCHEMA_MISMATCH`, безопасный резервный ответ.
3. **Ollama недоступна или зависла** → таймаут, ограничение длины ответа, автоматический резерв в режим mock, причина в аудите.
4. **Утечка секретов** → секретов в проекте нет; настройки в `.env.example`, `.env` и `data/` в `.gitignore`.
5. **Ложные совпадения поиска** (поиск по словам) → порог покрытия слов вопроса, вес редких слов, стоп-слова; тест на «ложную» близость («команда» и «командировка»); при сомнении система отказывает, а не выдумывает.
6. **Конфиденциальные данные в базе знаний** → всё работает локально, данные не уходят во внешние сервисы; в README и защите сказано, что пароли и персональные данные в базу знаний класть нельзя.
7. **Нет прозрачности, «почему так»** → каждая команда пишется в `audit_runs` (вход, выход, статус, причина, время), карточка вопроса показывает сырой вывод.

## 3 строки для портфолио
- **Проблема:** знания команды разбросаны по документам, поиск долгий, а ответы «по памяти» бывают неверными.
- **Решение:** локальный сервис на FastAPI + SQLite: поиск по абзацам, ответ только по найденному с цитатами, режимы с моделью (Ollama) и без, проверка JSON и цитат, ручная проверка и аудит всех запусков.
- **Результат:** 7 из 7 вопросов с ответом в базе получили источник из нужного документа, 3 из 3 вопросов без ответа честно ушли на ручную проверку; запуск за 5 минут без интернета.

## Сложности и как решал
- **Ложные совпадения при поиске.** Сначала фильтр был слишком строгим: лишние слова в вопросе («даётся», «означает») не давали найти ответ, при этом «команда» совпадала с «командировка». Решение: нормализация окончаний вместо обрезки, стоп-слова вопросительных глаголов, заголовок документа участвует в поиске, вес слов вопроса, которых нет в базе, равен весу «среднего» найденного слова. Результат на тестовом наборе — 10 из 10.
- **Зависание локальной модели.** При первом прогоне с Ollama запрос к `qwen3.5` не завершался: модель уходила в бесконечную генерацию. Нашёл причину замером, добавил лимит длины вывода (`num_predict`) и таймаут, а при сбое сервис отвечает резервным режимом, причина пишется в аудит.
- **Честность «уверенности» в режиме без модели.** Уверенность считается по доле слов вопроса, найденных в контексте, а не по выбранным предложениям.
- **Читаемые цитаты.** Предложения склеиваются из переносов строк, маркеры списков убираются, при этом цитата остаётся дословно проверяемой по тексту документа.

## План развития
Поиск по смыслу (локальные эмбеддинги), загрузка PDF/DOCX, права доступа к документам, оценка «ответ полезен / нет» для подбора порога, уведомления авторам документов по темам с частыми «непонятными» вопросами, поддержка нескольких команд.
